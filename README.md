## Before you do anything else: run Phase 0

This code was written in a sandboxed environment with no .NET SDK and no network
access to Yahoo Finance or NSE. None of it has been compiled, run, or tested
against live data or a real SDK. Do not trust it until you have run:

    cd tools/DataAccessSmokeTest
    dotnet run

This hits Yahoo's chart endpoint and NSE Indices' constituent list live, with no
dependency on the rest of the solution. If any check fails, the output tells you
specifically what to fix.

Known risk areas, called out in code comments:
- Yahoo's chart endpoint is unofficial and undocumented (see YahooChartResponse.cs
  and YahooFinanceMarketDataProvider.cs).
- NSE Indices is known to block plain HTTP clients. NseIndicesUniverseProvider
  implements session-replay as the primary workaround; a headless-browser fetch
  is the documented fallback if that is insufficient.
- ZerodhaMarketDataProvider.ResolveInstrumentTokenAsync throws NotImplementedException
  deliberately. Kite Connect needs a numeric instrument token, and this should
  reuse NiftySMC/NiftyOptionsSMC's existing instrument-master lookup rather than
  reimplementing it blind.
- IBrokerCredentialProvider is registered with a placeholder that throws if
  invoked. Wire real credential reuse before touching live broker data.
- FallbackMarketDataRouter.ResolveProviderSymbolAsync requires an explicit
  SymbolMapping row for the broker provider (no safe default exists, unlike
  Yahoo's .NS-suffix convention). Populate SymbolMapping before broker-sourced
  fetches will work.

## Getting started: setup, backfill, running a scan, broker credentials

This is the §25 deliverable checklist's "setup, backfill process, how to run
a scan, and broker-credential setup" walkthrough — the individual pieces
were already documented (Phase 0 above, `--help` text per command), but not
as one connected first-time sequence. Run these in order from a clean
database:

1. **Setup.** `dotnet restore && dotnet build`, then run Phase 0
   (`tools/DataAccessSmokeTest`) per the section above before touching
   anything else — this build has never been compiled or run against live
   data, so treat that check as load-bearing, not optional.

2. **Apply the schema.** `dotnet run -- db migrate` (from either
   `src/NiftyMicrocapEngine.Cli` or `src/NiftyMicrocapEngine.Web` — both
   apply the same migrations against the connection string in their own
   `appsettings.json`'s `Storage:SqliteConnectionString`). Creates every
   table in §18 against a fresh SQLite file; safe to re-run, since
   `MigrationRunner` tracks which migrations already applied.

3. **Fetch the universe.** `dotnet run -- universe fetch`. Pulls the
   current Nifty Microcap 250 constituent list from NSE Indices, upserts
   every constituent into `Symbols`, and records a new `UniverseSnapshots`
   row (§6.5's versioned-snapshot model — re-running this later creates a
   NEW snapshot rather than mutating the old one, so a backtest replaying a
   past date sees the constituent list that was actually in force then).
   This is the one step that has no fallback if NSE Indices' anti-bot
   session-replay (see Phase 0's "known risk areas") doesn't work from
   wherever this runs — the Phase 0 smoke test's second check exists
   specifically to catch that before it surfaces here.

4. **Backfill historical candles — this step is implicit, not a separate
   command.** There is no dedicated `backfill` CLI command. The first time
   `dotnet run -- scan` (or a backtest, or the dashboard) requests candles
   for a symbol/timeframe/date-range that isn't cached yet,
   `CachingMarketDataService` fetches the missing range from the routed
   provider (Yahoo for Daily/Weekly, the broker for intraday — see
   `DataProviderRouting` in `appsettings.json`) and persists it to
   `Candles` before returning it — see `CachingMarketDataService.cs`'s own
   doc comment. Concretely: the first `scan` run against a fresh database
   fetches roughly 2 years of Daily/Weekly history per symbol (matching
   `UniverseScanner.Stage1.cs`'s `asOfDate.AddYears(-2)` lookback) — expect
   this first run to take meaningfully longer than every subsequent one,
   which reads from cache and only fetches the small delta since the last
   run. There's no progress indicator for this beyond the `scan` command's
   own Stage 1/Stage 2 console output; a 250-symbol cold backfill through
   Yahoo at `DataProviders:Yahoo:RequestsPerSecond` (default 2/sec) is
   rate-limited by design (§3.4's resilience policy), so budget real wall-clock
   time for it, not just CPU time.

5. **Run a scan.** `dotnet run -- scan [yyyy-MM-dd]` (defaults to today).
   Or start the Web host and use the dashboard's "Run Scan" button, or hit
   `GET /api/scan`. `dotnet run -- benchmark` afterward shows Stage 1/Stage
   2 timings from `ScanHistory`.

6. **Broker credentials — only needed for intraday (H1/M30/M15) data.**
   Daily/Weekly data (Yahoo) needs no credentials at all; Stage 1 of a scan
   works fully without ever touching this. Stage 2's intraday MTF layers
   and anything hitting `DataProviderRouting`'s `Broker`-routed timeframes
   need a real `IBrokerCredentialProvider`. The default registered
   implementation, `NotConfiguredBrokerCredentialProvider`
   (`Infrastructure.BrokerData/IBrokerCredentialProvider.cs`), throws
   `InvalidOperationException` with an explicit message if anything actually
   calls it — Stage 1-only usage (Daily/Weekly, no intraday) never triggers
   this, so a fresh setup can validate everything up through Stage 1 before
   broker credentials exist at all. To wire real credentials: implement
   `IBrokerCredentialProvider.GetAccessTokenAsync()` — per an earlier
   decision, this should reuse the existing Zerodha/Upstox token store from
   the sibling NiftySMC-family systems rather than re-implementing OAuth
   here — and register it in place of `NotConfiguredBrokerCredentialProvider`
   in both hosts' `AddBrokerDataProvider()` call
   (`Infrastructure.BrokerData/ServiceCollectionExtensions.cs`). Separately,
   `FallbackMarketDataRouter.ResolveProviderSymbolAsync` needs an explicit
   `SymbolMapping` row per symbol for the broker provider before
   broker-sourced fetches will resolve (no safe default exists, unlike
   Yahoo's `.NS`-suffix convention) — populate that alongside wiring
   credentials, not after.

## Architecture notes worth knowing before extending this

The IBarProcessor pipeline is the backbone. Every indicator and every structure-
engine component is an IBarProcessor with a Priority. Lower-priority processors
run first and write to a shared IProcessingContext; higher-priority processors
read from it. This is how ATR feeds SuperTrend, how VolumeSMA feeds VolumeSpike,
how StdDev feeds Bollinger Bands, and how the five structure-engine stages
(swings, breaks, legs, zones, events) chain together without direct coupling
between the classes. StructureAnalysisPipelineFactory.Create() assembles a
correctly-ordered pipeline for one symbol and timeframe — use it rather than
hand-wiring processors, since getting the Priority values right is easy to get wrong.

Config property names match the appsettings.json keys in the build spec exactly,
even where that made for slightly awkward C# names — this was a deliberate late
fix after an earlier draft used its own naming and would have silently failed to
bind against the documented config shape.

## Honesty notes on scope

### Closed this pass (a real correctness bug, not just new scope)

- **Decision Engine indicator wiring — the most important fix in this pass.**
  `UniverseScanner.DecisionInput.cs` built the Decision Engine's
  `IndicatorValues` dictionary as **always empty**, with a comment claiming
  graceful degradation. But `DecisionEngine.LayersPart1/2.cs` reads specific
  keys from it (`EMA_20`, `EMA_50`, `ADX_14`, `RSI_14`, `MACD_12_26_9`,
  `Stochastic_14_3`, `OBV`, `HistVol_20`) to score the Trend, Momentum,
  Volume, and Volatility layers — 65 of the 100 confidence points. Since the
  dict was never populated, every scan run before this pass silently scored
  those four layers on partial/default logic only, for every symbol, every
  run. The indicators themselves WERE being computed correctly (they run as
  `IBarProcessor`s inside `StructureAnalysisPipelineFactory`'s pipeline) —
  they just never got read back out into what the Decision Engine actually
  sees. Fixed by exposing every indicator instance via
  `StructureAnalysisPipelineFactory.Handles.SnapshotIndicatorValues()` and
  having `UniverseScanner.DecisionInput.cs` call it instead of building an
  empty dictionary. Low-risk, additive change — verified no other caller
  constructs `Handles` positionally or depends on its old shape.
- **StructureEventType schema gap (previously flagged, now fixed)**: the
  domain enum was missing `BullTrap`/`BearTrap`/`FalseBreakout`/
  `FailedBreakdown`/`VolumeAbsorption`/three `Gap*` kinds that the structure
  engine's `SmcEventDetector` actually detects — they were falling through
  `MapSmcEventKind`'s default case and only logged at Debug instead of
  persisted. `EventType` is stored as SQLite TEXT with no CHECK constraint,
  so adding enum members needed no migration.
- **ScanHistory table was never written to.** It existed in the schema since
  the first migration but nothing populated it, so there was no timing
  history behind the section 23/25 benchmark deliverable beyond whatever a
  single run's console output showed. `UniverseScanner.RunAsync` now saves
  one row per completed run (fail-soft — a persistence failure here doesn't
  fail the scan itself); `dotnet run -- benchmark [n]` reports it.
- **Reconciliation job now has a scheduler**, closing part of the "nothing
  schedules this automatically" gap flagged below in previous passes.
  `ReconciliationSchedulerHostedService` (Web project only — the CLI never
  calls `host.RunAsync`, so a `BackgroundService` registered there would
  never actually run) runs the existing job daily at a configured IST hour
  via the codebase's existing `IndiaStandardTime` utility. **Opt-in**:
  `Reconciliation:ScheduledEnabled` defaults to `false` — a hosted service
  silently hitting Yahoo on an implicit schedule seemed worse than requiring
  an explicit flip in appsettings.
- **Walk-forward backtester (section 24, Phase 6 — "Validation")**, the next
  unstarted phase in the spec's own roadmap. New `Backtesting` namespace:
  `WalkForwardBacktester` walks a configurable window of historical as-of
  dates per symbol, running the SAME engines the live Scanner runs
  (structure pipeline, MTF, Regime Filter, Decision Engine, Trade Plan
  Builder) using only candles closed on or before each as-of date, then
  `BacktestOutcomeSimulator` walks forward to see whether each Buy/StrongBuy
  signal's stop or target got hit first. `BacktestReportFormatter` writes a
  Markdown summary (bucket-level win rate / expected-R stats — this is what
  section 24's "weight/threshold tuning" deliverable actually needs: raw
  material for a human to compare buckets against, not a black-box
  optimizer picking new DecisionEngineOptions weights, which would carry its
  own overfitting risk this pass isn't positioned to judge) plus a
  trade-level CSV. Exposed via `dotnet run -- backtest [from] [to]
  [maxSymbols]`, writing to `./backtest-reports/`.
  **Deliberately does NOT reuse UniverseScanner's private per-symbol
  methods** — the live Scanner caches broad-market/regime context ONCE per
  run (correct for a live "today" scan), but a walk-forward backtest needs a
  DIFFERENT regime snapshot at every simulated as-of date, since regime
  state genuinely changes across a backtest window. The per-date evaluation
  logic in `WalkForwardBacktester` intentionally mirrors
  `UniverseScanner.Stage1.cs`/`DecisionInput.cs`/`TradePlan.cs` step for
  step (duplicated, not extracted into a shared helper, to avoid touching a
  working, already-tested class for this addition) — if that logic changes,
  this needs a matching update. **Not yet run against real data** in this
  sandbox (no .NET SDK, no network access to NuGet here — see below), so
  treat the sample report format as reviewed-by-inspection, not
  execution-verified.

### Production-readiness and performance (prior pass, still accurate)

- **Retry/backoff**: every outbound HTTP call (Yahoo, NSE, Zerodha) now goes
  through a RetryHandler implementing exponential backoff with jitter for
  transient failures (5xx, 408, 429, network exceptions), reading
  DataProviders:*:RetryCount from config rather than a hardcoded count. Built
  on plain BCL DelegatingHandlers rather than adding a Polly dependency this
  sandbox couldn't verify would restore cleanly with no network access —
  swap for Microsoft.Extensions.Http.Resilience in a real deployment if
  richer policies (circuit breakers, jittered strategies) are wanted.
- **Rate limiting**: a token-bucket RateLimitingHandler (built on the .NET 8
  BCL's System.Threading.RateLimiting, one new package) enforces
  DataProviders:Yahoo:RequestsPerSecond so a 250-symbol Stage 1 scan can't
  fire requests faster than Yahoo's unofficial endpoint can reasonably
  tolerate — self-imposed, since neither Yahoo nor NSE publish an actual
  rate contract for this engine to respect.
- **Config validation on startup**: five IValidateOptions<T> validators
  (DecisionEngine, MultiTimeframe, DataQualityGate, RiskManager,
  Reconciliation) catch the configuration mistakes most likely to produce
  silently-wrong output rather than an obvious crash — layer weights not
  summing to 100, thresholds out of order, a data-quality gate no symbol
  could ever pass, a zero StopAtrMultiple. The Web project (a real
  long-running host) uses ASP.NET Core's ValidateOnStart mechanism; the CLI
  (a one-shot command dispatcher that never calls host.RunAsync/StartAsync,
  so that mechanism never fires) explicitly resolves each validated
  IOptions<T> right after host.Build() instead. Also fixed a real bug found
  while wiring this: the Web project was missing the ReconciliationOptions
  config binding entirely, so its reconciliation endpoint was silently
  running on unconfigured defaults regardless of appsettings.json.
- **Per-symbol scan resilience**: Stage 1 and Stage 2 both now wrap each
  symbol's evaluation in its own try/catch. One symbol's exception (a bad
  candle, an exhausted-retries timeout, an unexpected data shape) is logged
  and recorded as an exclusion rather than crashing the other 249 symbols in
  the batch — previously a single bad symbol would take down the entire
  scan run.
- **Stage 1/Stage 2 parallelization**: both loops now run with bounded
  concurrency (ScannerOptions:MaxDegreeOfParallelism, default 8, via
  SemaphoreSlim + Task.WhenAll) instead of a strictly sequential foreach.
  Section 17's "well under 5 minutes" target for 250 symbols isn't
  realistically achievable sequentially once live HTTP fetches are
  involved. Verified with a test asserting observed concurrency never
  exceeds the configured max, alongside the existing resilience test
  re-verified under the concurrent implementation. One real characteristic
  flagged rather than hidden: every repository write goes through SQLite,
  which serializes writes at the database-file level regardless of
  application-level parallelism — higher MaxDegreeOfParallelism speeds up
  the network-bound work but write-heavy phases still effectively serialize
  at the SQLite layer. Expected behavior for this schema's intended scale,
  not a bug.
- **Structured logging**: scan-start, Stage 1 completion, Stage 2/run
  completion, and every per-symbol failure now log through ILogger with
  structured fields (symbol, duration, counts) rather than the previous
  near-silence — an operator can now tell what a scan run actually did from
  the log stream alone, without attaching a debugger.

### Closed this session (production-readiness pass)

- **A real, systemic timezone bug — the most consequential finding of this
  session.** Every place in this codebase that converted a `DateOnly` into
  a query boundary (`UniverseScanner.Stage1.cs`/`Stage2.cs`,
  `BroadMarketContextProvider.cs`, `WalkForwardBacktester.cs`,
  `DashboardEndpoints.GetChart`) did it via
  `someDateOnly.ToDateTime(TimeOnly.MinValue/MaxValue)` passed directly
  wherever a `DateTimeOffset` was expected. `DateOnly.ToDateTime(TimeOnly)`
  returns `Kind=Unspecified`, and the implicit `DateTime`→`DateTimeOffset`
  conversion for Unspecified Kind uses **the running process's local system
  timezone**, not UTC. Every candle this system actually stores comes from
  `DateTimeOffset.FromUnixTimeSeconds(...)` (`YahooFinanceMarketDataProvider`)
  — always `+00:00`. `SqliteCandleRepository` stores and compares
  `Timestamp` as ISO-8601 TEXT via a plain SQL `>= / <=` — a **lexicographic**
  string comparison, not a timezone-aware one. A boundary built on any
  machine whose local timezone isn't UTC (an IST-configured dev machine,
  plausible here) sorts wrong relative to the `+00:00`-stored candles — the
  bug is invisible on a UTC-configured deployment box, which is exactly why
  it could ship unnoticed. One place already did this correctly —
  `SqliteUniverseRepository.cs`'s `new DateTimeOffset(dateTime,
  TimeSpan.Zero)` — this pass generalized that fix into
  `DateOnlyExtensions.ToUtcDateTimeOffset(this DateOnly, TimeOnly)` (Domain
  project) and replaced all 11 call sites. Two new tests
  (`SqliteCandleRepositoryNoRepaintTests.cs`) verify this against a real
  in-memory SQLite database (not a fake) — one confirms the fix excludes
  out-of-range candles correctly, the other documents the bug itself by
  hand-tracing exactly how a `+05:30` boundary string-sorts against a
  `+00:00`-stored candle.
- **Scanner scheduling** — `ScanSchedulerHostedService` (Web host only,
  same reasoning as reconciliation's), opt-in via `Scanner:ScheduledEnabled`
  (default false), configurable `Scanner:ScheduledHourIst` (default 16 = 4
  PM IST, after NSE close and before Reconciliation's default 8 PM slot).
  The IST daily-scheduling math (`TimeUntilNextRun`) was extracted from
  `ReconciliationSchedulerHostedService` into a shared
  `IstDailyScheduler.TimeUntilNextRun` rather than duplicated a second time.
  This closes Phase 7's "the Scanner itself still has no schedule" gap —
  every production-automatable job in this system (scan, reconciliation)
  now has one, both opt-in.
- **SQLite write resilience.** Every write method across all 8 repository
  classes (11 methods total — `SaveAsync`/`UpsertAsync`/etc.) is now
  wrapped in `SqliteRetry`, a small BCL-only retry (matching
  `RetryHandler`'s existing HTTP-retry shape, not a new Polly dependency)
  that retries on `SQLITE_BUSY`/`SQLITE_LOCKED` with exponential backoff
  and jitter. SQLite serializes writers, so this is scoped to writes only
  — reads aren't wrapped, since retrying a read that hit contention would
  mostly mask a genuinely stuck writer rather than smooth over ordinary
  use. `SqliteRetryTests.cs` verifies the retry/no-retry/give-up behavior
  against real `SqliteException` instances.
- **Golden-file RSI test** (`RsiGoldenFileTests.cs`) — cross-checked
  against StockCharts.com's published Wilder smoothing formula and a
  numeric worked example from docs.supra.com, not just internal
  self-consistency. The 7-point close series was reconstructed from the
  source's stated per-period gain/loss figures plus its one explicit price
  anchor ("price went from 26 to 25"); the final assertion (75.68, not the
  source's rounded 75.67) is deliberate — RS = 1.12/0.36 is a repeating
  decimal, and the source rounds it to 3.11 before computing RSI, whereas
  this codebase's RsiIndicator (correctly) carries full precision through
  to the final value. See the test file's doc comment for the full
  reasoning.
- **§6.8's real NSE circuit-band feed — the last item on Phase 7's own
  checklist.** Previously flagged as needing live network access to verify
  before attempting; verified this session (via web search + a direct
  fetch) that `https://nsearchives.nseindia.com/content/equities/sec_list.csv`
  is a live, publicly reachable (no auth, no session/anti-bot friction
  unlike nseindia.com's main site), NSE-published CSV of every symbol's
  current price band. `INseCircuitBandProvider`/`NseCircuitBandProvider`
  (`Infrastructure.BrokerData/Nse/`) fetch and cache it (12-hour cache —
  the feed changes roughly daily, occasionally mid-session via a
  surveillance action); `ICircuitBandTracker` gained a band-aware overload
  (backward compatible — the original 2-argument signature still works
  identically) that flags a lock from a close that moved the full band
  percentage even without the original zero-intraday-range signature,
  closing the exact under-detection case that heuristic's own doc comment
  flagged. Wired into `UniverseScanner` (fetched once per run, same
  pattern as broad-market context) — not into `WalkForwardBacktester`,
  which keeps the zero-range-only heuristic deliberately, to bound this
  session's scope. `NseCircuitBandProviderParseTests.cs` tests the CSV
  parser (including the real observed quirk of one symbol appearing under
  multiple Series at different bands — EQ is preferred) against a sample
  matching the live file's actual structure; `CircuitBandTrackerTests.cs`
  gained band-aware cases. **The HTTP fetch/cache path itself has not been
  exercised against a live call in this sandbox** (no network access here
  either) — only the parser and the tracker's decision logic are
  execution-adjacent; the fetch path is reviewed by inspection, matching
  every other HTTP-touching piece of this build.

- **Dashboard scan-result caching.** `RunScan`/`GetDrillDown` previously
  re-ran the full 250-symbol Scanner on every single API call — clicking
  through 5 symbols in the Symbol Drill-Down view meant 5 full universe
  scans. `DashboardEndpoints.GetOrRunScanAsync` now caches the last
  `ScanRunResult` per as-of date in an `IMemoryCache` (15-minute expiry,
  double-checked locking to avoid a cache stampede on a cold/expired
  entry). "Run Scan" always passes `refresh=true` and bypasses the cache
  (an explicit user action means "run one now"); Drill-Down reuses whatever
  scan is cached. `GetChart` is deliberately NOT included in this — it
  re-runs the structure pipeline for one symbol, not a 250-symbol scan, so
  the cost this fix targets doesn't apply there in the same way.

- **Backtester limitations worth knowing before trusting its output**: (1)
  it re-runs the full structure/indicator pipeline from scratch at every
  simulated as-of date per symbol — the same cost the live Stage 1 pays once
  per "today," paid many times over in a backtest, which is why
  `BacktestRequest.MaxSymbols` defaults to a conservative 30 rather than the
  full 250; (2) same-bar stop/target ambiguity is resolved conservatively
  (assume stop-first — see `BacktestOutcomeSimulator`'s doc comment), which
  will understate win rate somewhat versus a real intraday-path-aware
  simulation; (3) it has NOT been run against real data in this sandbox, so
  the report format and aggregation logic are reviewed-by-inspection only,
  not execution-verified — run it yourself before trusting any number it
  produces; (4) it is intentionally NOT wired to automatically retune
  `DecisionEngineOptions`' weights from its own output — that's a
  human-in-the-loop judgment call about overfitting risk, not something
  this pass automated; (5) it still uses the zero-range-only circuit
  heuristic (see above).
- **The entire test suite (old and new) has never actually been
  executed anywhere in this sandbox** — no .NET SDK, no NuGet network
  access. Every test file across every pass this build went through —
  including all the new coverage this session
  (`SqliteRetryTests.cs`, `RsiGoldenFileTests.cs`,
  `NseCircuitBandProviderParseTests.cs`, the extended
  `CircuitBandTrackerTests.cs`, `SqliteCandleRepositoryNoRepaintTests.cs`,
  `ExtendedIndicatorTests.cs`, `BacktestOutcomeSimulatorTests.cs`,
  `WalkForwardBacktesterTests.cs`) — has been reviewed by careful manual
  tracing against the actual formulas/signatures involved, not by running
  `dotnet test`. This is the single most important caveat on this entire
  codebase: **treat everything here as reviewed, not verified, until it's
  actually been built and run.** One real risk worth flagging specifically:

  `NotEmpty(reportA.Trades)`, which depends on a synthetic "up" trend

  6-month window — if that assertion fails on a real run, tune the
  fixture's window/trend strength before assuming it's a backtester bug.

### Judgment calls worth knowing about

- The Risk Manager's stop formula: section 16.1 states the stop as
  "max(structural stop, entry - 1.5xATR14)" for a long, but read literally on
  raw price values that would produce the TIGHTER of the two stops —
  backwards from the section's own stated rationale ("the ATR floor prevents
  unrealistically tight stops"). The implementation takes whichever candidate
  is FURTHER from entry instead, matching the stated intent rather than a
  literal reading of "max" — flagged in TradePlanBuilder's code comments for
  you to override if the literal reading was actually intended.
- The Decision Engine's per-layer scoring heuristics (which specific
  indicator thresholds contribute how many of a layer's points) are a
  reasonable-first-pass implementation of section 14's descriptive rules, not
  a literal transcription — section 14 describes the layers and their point
  budgets but leaves the exact sub-scoring logic to the implementer. Revisit
  against real chart examples during the spec's own Phase 6 validation pass.
- The audited regime-filter short-circuit fix is covered by a real regression
  test against the production DecisionEngine implementation, not a fake.
